PREFILL VS DECODE

Why does an LLM read your prompt fast but write its answer slowly?

Every LLM request runs in two phases. Prefill reads your whole prompt at once. Decode writes the answer one token at a time. They hit completely different limits on the GPU, and that one fact explains most of LLM inference.

Prefill is compute-bound

All prompt tokens go through the model together. The weights are read once and reused for every token, so the GPU's maths units are the limit.

Decode is memory-bound

To make one token, the GPU reads every weight from memory and does only a little maths with each. So it spends almost all its time waiting for data.

Roofline: below about 295 FLOPs per byte (the knee), speed is capped by memory; above it, by compute. Llama 3.1 8B, weights only, ideal. Real engines also read each user's KV cache, which pulls the knee further right.

06

Two phases, two latency numbers

Prefill → TTFT

Time to first token

How long you wait before the first word appears. Grows with prompt length. Matters most for chat and voice.

Decode → ITL / TPS

Inter-token latency

The gap between each word as it streams. An ITL of 10 ms means 100 tokens per second for that user. Grows with model size and batch size.

"Tokens per second" can mean per user (latency) or for the whole service (throughput). Always ask which one.

07

When the phases collide

On a shared GPU, only one phase runs at a time. A long prefill pauses everyone's streaming; lots of decoding delays new users' first token. Two fixes:

Chunked prefill

Cut long prompts into chunks and mix them into decode batches, scheduling decode first. Streaming stays smooth. It's on by default in vLLM V1.

Disaggregation

Run prefill and decode on separate GPUs, each tuned and scaled for its own limit. Better tail latency, but the KV cache must be copied across. On small or mistuned setups it can be 20–30% slower, and short prompts are often faster prefilled locally.

09

Your LLM feels slow. Diagnose it

  1. 1

    Measure TTFT and ITL separately

    One blended "latency" number hides which phase is the problem. Look at P50 and P90, not just the average.

  2. 2

    High TTFT? Look at prefill

    Long prompts, no prefix caching, or prefill stuck behind other work. Try prefix caching, chunked prefill, or shorter prompts.

  3. 3

    High ITL? Look at decode

    Big model, huge batches, long KV caches. Try quantization, speculative decoding, or a smaller model.

  4. 4

    Low throughput, GPU "busy" but slow?

    Probably memory-bound decode at small batch sizes. Batch more users together (continuous batching).

10

Interview follow-ups

Why is decode memory-bound but prefill compute-bound?

Both read the model's weights once per forward pass. Prefill does maths for thousands of prompt tokens with that one read, so it has hundreds or thousands of FLOPs per byte and saturates compute. Decode makes one token per pass per user, about 1 FLOP per byte in 16-bit, far below the GPU's ~295, so it waits on memory bandwidth.

What does the KV cache have to do with this?

Prefill builds the KV cache: the keys and values for every prompt token. Decode reuses it, adding one entry per new token, so it never recomputes the past. But the cache grows with context length and batch size and must also be read every step, which makes decode even more memory-bound.

Why does batching raise throughput but not per-user speed?

In the memory-bound region, a step takes about the time to read the weights, whether it serves 1 user or 64. So total tokens per second grows almost linearly with batch size while each user's speed stays roughly flat, until you hit the compute limit or the KV cache fills memory.

How would you estimate the max tokens per second for a model?

For one user: memory bandwidth ÷ bytes of weights. An 8B model in 16-bit is 16 GB; an H100 moves 3.35 TB/s, so about 210 tokens/s at best. Real numbers are lower because of the KV cache, kernels and overheads, but it's a solid first estimate.

When would you disaggregate prefill and decode?

At scale, with long prompts and strict latency targets, where prefill spikes hurt streaming. Not for small deployments or short or heavily cached prompts: copying the KV cache between machines costs time and can make things slower.
